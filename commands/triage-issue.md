# /ai-workspace:triage-issue

受け取った Issue やタスクが、今ある機能の不具合か、まだ無い機能の追加かを見分ける。不具合なら原因を証拠で突き止め、新しい機能なら既存の作りに沿った設計を出す。コードは直さない。直すのは `/ai-workspace:implement` の役目。

引数: `$ARGUMENTS`（タスクの説明と Issue 番号。番号だけのこともある）

## 行動原則

- 結論はすべて、コード・ログ・コマンドの結果で裏付ける。裏付けの無いものは「推測」と書く
- 一度に全部を説明しようとせず、候補を1つずつ確かめて絞り込む
- 何を試し、何が分かり、なぜそう判断したかを報告に残す
- 足りない情報は AskUserQuestion で聞く

## Step 1: 分ける

Issue 番号があれば `gh issue view <番号> --json title,body,labels,comments` で中身を取る。次の手がかりで分ける。
- 不具合: 今ある機能が期待どおりに動かない（エラーになる、結果が違う、遅い）
- 新しい機能: まだ無い振る舞いを足してほしい

ラベル、本文の書き方（「動かない」か「ほしい」か）、既存の画面や API への言及を手がかりにする。どちらとも決められなければ AskUserQuestion で聞く。

## Step 2a: 不具合を調べる

1. 再現する: 報告どおりの入力と手順で、手元で同じ結果になるかを確かめる。入力・環境・タイミングのどれが効いているかを絞り、毎回起きるか、ときどき起きるかを記録する
2. 範囲を見る: 関係するファイルを探し、`git log` と `git blame` で最近の変更を確かめる
3. 原因の候補を立てる。状況に合う見方を選ぶ
   - 「なぜ」を繰り返し、現象から設計上の前提までさかのぼる
   - 同時に動く処理があれば、共有しているデータと順番を調べる
   - 状態が絡むなら、正しい移り変わりと、異常が起きる移り変わりを並べる
   - 動いていた版があれば、差分を比べる（`git bisect` など）
   - 手がかりが足りなければ、どこにログを足せば分かるかを挙げる
4. 確かめる: 候補ごとに、最小の再現手順やデバッガで当たり外れを確かめる。外れたら次の候補に移る

## Step 2b: 新しい機能を設計する

1. 似た機能を探す: 今のコードで一番近い機能を探し、ディレクトリ構成・層の分け方・命名・使っているライブラリを確かめる
2. 機能を分ける: 小さな作業に分け、それぞれの入力と出力、作業どうしの順番を決める
3. 置き場所を決める: 足すファイル・直すファイルを、似た機能の置き方に合わせて決める
4. 境目を決める: 関数やクラスの形、既存コードとつなぐ所、必要な設定を決める

設計は、今ある作りをまねて、変更が一番少なくなる形を選ぶ。新しい書き方を持ち込まない。先の拡張を見越した抽象化はしない。

## Step 3: 報告する

次を短く報告する。因果や依存の関係は図を添える。
- 分けた結果（不具合 / 新しい機能）とその根拠
- 不具合: 再現の条件、原因、原因と確かめた方法、影響の範囲、直し方の方向
- 新しい機能: 足すファイルと直すファイル、作業の順番、気をつける境界の条件
- 次にやること

ユーザーがレポートとしてまとめるよう求めたときだけ、同じ中身を1つの文書にまとめる。Issue にコメントするのは、投稿する中身を見せて AskUserQuestion で許可を得たときだけにする。
