# /ai-workspace:implement

タスクを受け取り、今あるコードに合わせて実装し、ビルドとテストが通るまで確かめる。計画を出すだけで終わらせない。

引数: `$ARGUMENTS`

## Step 1: 何を作るかを決める

- Issue 番号なら `gh issue view <番号> --json title,body,labels` で中身を取る
- 文章なら、その文章から読み取る
- 何を作るか、どこを変えるか、何ができたら終わりかが読み取れなければ、AskUserQuestion で聞く

作業を小さく分けてから始める。

## Step 2: 書く前に調べる

この手順を飛ばさない。飛ばすと、すでにある処理を作り直したり、命名やエラー処理が周りとずれたり、前に指摘された誤りを繰り返したりする。

1. 同じ種類の処理がすでにあるかを Glob と Grep で探す。あれば、その命名・エラー処理・ファイルの置き方・層の分け方に合わせる
2. 同じ範囲の過去の PR と Issue を `gh pr list --search "<語>"`、`gh issue list --search "<語>"` で探し、レビューで受けた指摘を確かめる。同じ指摘を受けないように書く
3. 新しいファイルやディレクトリを作るときは、似た機能の置き方に合わせる

似た処理が見つからないとき、または周りと違うやり方を取るときは、書く前にユーザーへ一言伝える。

## Step 3: 書く

- 一番単純な形で、変える量を最小にする
- Step 2 で確かめた書き方に合わせる
- 範囲に迷ったら AskUserQuestion で聞く

## Step 4: 確かめる

1. ビルドと型チェック: プロジェクトの設定ファイル（`package.json`、`pom.xml`、`build.gradle`、`pyproject.toml`、`Cargo.toml` など）から正しいコマンドを選んで実行する。失敗したら直して、通るまで繰り返す
2. テスト: テストがあれば実行する。失敗したら直して、通るまで繰り返す
3. 動かして確かめる: スクリプトや画面なら、実際に動かして結果を見る

## Step 5: コミット・push・PR

`git status` と `git diff` で変更を見直す。
- `--pr` があれば、コミット・push・PR 作成まで進める
- `--push` があれば、コミットと push まで進める
- どちらも無ければ、どこまで進めるか（何もしない / コミット / push / PR）を AskUserQuestion で聞く

既定ブランチには直接 push しない。作業ブランチが無ければ先に作る。PR は `gh pr create` で作り、本文は変更内容から書く。

## Step 6: 報告する

次を短く書く。
- 作ったものと変えたファイル
- ビルド・テスト・動作確認の結果
- Step 2 で見つけて合わせた既存の書き方や過去の指摘
- コミット・push・PR をどこまで進めたか。進めていなければ、次に何をすればよいか

## 困ったとき

- ビルドの失敗が直せない: エラー、試したこと、変えたファイルを伝えて判断を仰ぐ
- 依存関係の問題: 原因と直し方の候補を出し、どれで進めるかを聞く
